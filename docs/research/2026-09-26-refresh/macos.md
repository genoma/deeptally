# Research: Correct platform-level refresh design for a rarely-changing remote value in a macOS 15+ menu bar app

Lane: refresh/timer/App-Nap/energy design. Scope: design the *most correct* mechanism (not the cheapest) for a Swift 6 + AppKit `NSStatusItem` + SwiftUI popover, `LSUIElement`, long-running app that polls one small HTTPS JSON document whose value changes only on spend/top-up.

All URLs were accessed during this run. The HIG page reported `Published Time: Fri, 25 Sep 2026 06:59:52 GMT`; Apple's documentation JSON carries a 2026 copyright. **Access date: 2026-09-25.** Labels used throughout: **VERIFIED** (source says it), **INFERRED** (my reasoning from sources), **UNKNOWN** (could not settle).

---

## Summary

1. **Primary conclusion (high confidence):** "Refresh when the user looks at it" is the correct *primary* mechanism, with a long, OS-deferrable timer only as a backstop — this is what Apple's own guidance implies, not a cost-cutting compromise. Apple: *"Eliminate unnecessary, non-user-driven work and wait for user input. Don't poll for state changes … and don't perform power-intensive, discretionary operations when the system is running on battery power"* and *"Power-intensive operations should be under the user's control"* (Energy Efficiency Guide for Mac Apps). A status-item-only `LSUIElement` app has no visible windows, which is precisely Apple's App Nap candidacy criterion, and App Nap *"completely suspends your app's execution"* and does *"timer throttling, which reduces the frequency with which the app's timers are fired."*
2. **The current implementation is structurally right but mis-prioritised:** it has launch/wake/path/manual/settings triggers and a 20 min fixed default with backoff + jitter, but **it has no refresh-on-look trigger**, and it ignores the OS's own power/network state inputs (Low Power Mode, constrained/expensive path, battery). Opening the popover must fetch-if-stale; that single change does more for perceived correctness than any timer tuning.
3. **Recommended policy (judgment, INFERRED):** nominal backstop **30 min on AC, 60 min on battery or Low Power Mode, floor 10 min**, `tolerance ≥ 10 % of the interval` (Apple's documented guideline), plus a persisted per-install random offset ≤ 60 s; a 90 s freshness window in front of every trigger; exponential backoff ×2 capped at 1 h with full jitter; skip opportunistic polls when the path is constrained or expensive.
4. **Concrete API verdict:** use a **one-shot `DispatchSourceTimer` armed with `wallDeadline:` and an explicit `leeway`**, re-armed per cycle from policy — its leeway and sleep semantics are the only ones Apple documents precisely. Avoid `Timer` (run-loop-mode dependent; the classic "menu-bar timer pauses while the menu is open" bug). `Task.sleep(until:tolerance:)` on `ContinuousClock` (macOS 13+) is an acceptable equivalent for the authoring model, but its tolerance→kernel-leeway mapping is undocumented. **`NSBackgroundActivityScheduler` is not the right primary tool** (it is a discretionary DAS/CTS maintenance scheduler that can fire *before* its nominal date and can be deferred a lot), though Apple does list "periodic content fetches" and "intervals of 10 minutes or more" as intended uses — so it is a legitimate *optional backstop*, never the freshness guarantee.
5. **`schedulingAppliesToLowPowerMode` does not appear to exist.** As of the current Apple docs the class exposes exactly `identifier`, `repeats`, `interval`, `qualityOfService`, `shouldDefer`, `tolerance`. The real Low Power Mode API is `ProcessInfo.isLowPowerModeEnabled` + `NSProcessInfoPowerStateDidChange` (macOS 12+).

## Findings

### 1. Timer guidance: tolerance, coalescing, drift, sleep

1. **`Timer.tolerance` is one-sided, drift-free, and the system may add tolerance of its own.** **VERIFIED** — "The timer may fire at any time between its scheduled fire date and the scheduled fire date plus the tolerance. The timer will not fire before the scheduled fire date. For repeating timers, the next fire date is calculated from the original fire date regardless of tolerance applied at individual fire times, to avoid drift. The system reserves the right to apply a small amount of tolerance to certain timers regardless of the value of this property." Source: <https://developer.apple.com/documentation/foundation/timer/tolerance> (macOS 10.9+).
2. **A run-loop `Timer` may not fire at all while the run loop is in another mode.** **VERIFIED** — "A timer is not a real-time mechanism. If a timer's firing time occurs during a long run loop callout or while the run loop is in a mode that isn't monitoring the timer, the timer doesn't fire until the next time the run loop checks the timer. Therefore, the actual time at which a timer fires can be significantly later." Source: <https://developer.apple.com/documentation/foundation/timer>. This is the mechanism behind the widely-reported "my menu bar timer stops while the menu is open" class of bugs (**INFERRED**, corroborated by field reports such as <https://stackoverflow.com/questions/28883383/>). Mitigation if you insist on `Timer`: add it in `.common` modes.
3. **Dispatch timers have a *two-sided* delay budget and a hard leeway cap.** **VERIFIED** — "Any fire of the timer may be delayed by the system in order to improve power consumption and system performance. The upper limit to the allowable delay may be configured with the 'leeway' argument, **the lower limit is under the control of the system**. For the initial timer fire at 'start', the upper limit to the allowable delay is set to 'leeway' nanoseconds. For the subsequent timer fires at 'start' + N * 'interval', the upper limit is **MIN('leeway','interval'/2)**." Source: `dispatch_source_set_timer` header docs in <https://github.com/apple/swift-corelibs-libdispatch/blob/main/dispatch/source.h> and <https://developer.apple.com/documentation/dispatch/dispatch_source_set_timer> (macOS 10.6+). Practical consequence for a 20 min interval: leeway above 10 min is silently clamped, and **the OS may fire the timer *earlier* than you asked** — so never assume "at least N minutes between polls" from a dispatch timer.
4. **`DISPATCH_TIMER_STRICT` exists but is the wrong knob here.** **VERIFIED** — "CAUTION: Use of this flag may override power-saving techniques employed by the system and cause higher power consumption, so it must be used with care and only when absolutely necessary." (same header).
5. **Sleep semantics differ by clock choice, and this is documented for dispatch timers.** **VERIFIED** — "When a computer goes to sleep, all timer dispatch sources are suspended. When the computer wakes up, those timer dispatch sources are automatically woken up as well. … If you set up your timer dispatch source using the `dispatch_time` function or the `DISPATCH_TIME_NOW` constant, the timer dispatch source uses the default system clock to determine when to fire. However, the default clock does not advance while the computer is asleep. By contrast, when you set up your timer dispatch source using the `dispatch_walltime` function, the timer dispatch source tracks its firing time to the wall clock time. This latter option is typically appropriate for timers whose firing interval is relatively large because it prevents there from being too much drift between event times." Source: *Dispatch Sources* in the Concurrency Programming Guide, <https://developer.apple.com/library/archive/documentation/General/Conceptual/ConcurrencyProgrammingGuide/GCDWorkQueues/GCDWorkQueues.html>. **INFERRED:** an uptime-armed 20 min timer whose fire is swallowed by system sleep effectively restarts its count on wake (it can slide indefinitely), whereas a `wallDeadline` timer is overdue at wake. Because the *doc doesn't specify how promptly* a woken timer fires, a post-wake refresh must come from the wake trigger, not from the timer.
6. **Apple's documented tolerance guideline is ≥10 %.** **VERIFIED** — "A general guideline is to set the tolerance to at least 10 percent of the interval for a repeating timer … Even a small amount of tolerance has a significant positive impact on the energy usage of your app." and "The system will use this flexibility to shift the execution of timers by small amounts of time—within their tolerances—so that multiple timers can be executed at the same time." Source: <https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/Timers.html> (and the iOS twin, <https://developer.apple.com/library/archive/documentation/Performance/Conceptual/EnergyGuide-iOS/MinimizeTimerUse.html>).
7. **Swift concurrency: `Task.sleep(for:)` defaults to `ContinuousClock`, which keeps counting during system sleep.** **VERIFIED** — declaration shows `clock: C = .continuous` on `Task.sleep(for:tolerance:clock:)` (macOS 13+), and "A clock that measures time that always increments and **does not stop incrementing while the system is asleep**" (`ContinuousClock`), versus "…but **stops incrementing while the system is asleep**" (`SuspendingClock`). Sources: <https://developer.apple.com/documentation/swift/task/sleep(for:tolerance:clock:)>, <https://developer.apple.com/documentation/swift/continuousclock>, <https://developer.apple.com/documentation/swift/suspendingclock>. Consequence (**INFERRED**): a sleep deadline that elapses during machine sleep is already overdue at wake, so a naive loop fires immediately on wake — which is desirable, but combines with `didWake` to produce duplicate triggers that must be debounced.
8. **Swift's tolerance *is* coal
escing-aware, but the mechanism is undocumented.** **VERIFIED (doc text)** — "Suspend task execution until a given deadline within a tolerance. **If no tolerance is specified then the system may adjust the deadline to coalesce CPU wake-ups** to more efficiently process the wake-ups in a more power efficient manner." <https://developer.apple.com/documentation/swift/continuousclock/sleep(until:tolerance:)>. **UNKNOWN:** whether the `tolerance:` value reaches the kernel as `leeway`. The Swift runtime source for the related `sleep(nanoseconds:)` path shows a scheduling-executor call `enqueue(ExecutorJob(…), after: .nanoseconds(duration), clock: .continuous)` with a fallback `_enqueueJobGlobalWithDelay(duration, job)` and **no occurrence of "leeway"/"tolerance"** — <https://raw.githubusercontent.com/swiftlang/swift/main/stdlib/public/Concurrency/TaskSleep.swift>. So: do not claim measurable idle-wakeup accounting parity between `Task.sleep(tolerance:)` and a dispatch timer without measuring.
9. **Verdict for question 1 (INFERRED, medium-high confidence).** For a ≥10-minute periodic network poll, the three candidates are functionally equivalent in the happy path; the differentiators are documented leeway semantics (dispatch timer wins, and its leeway is explicitly clamped to `interval/2`), run-loop-mode fragility (`Timer` loses), sleep reconciliation (wall-clock arming is what you want for "refresh soon after wake"), cancellation ergonomics and Swift 6 actor integration (`Task.sleep` wins). Recommendation: one-shot dispatch timer with `wallDeadline` + explicit leeway, re-armed per cycle; use `Task.sleep(until:tolerance:)` only if you prefer the single-model concurrency style and accept the undocumented leeway mapping.

### 2. App Nap and throttling of a background `LSUIElement` app

10. **App Nap can suspend execution entirely and throttles timers.** **VERIFIED** — "**App Nap** reduces power consumption by **completely suspending your app's execution** when it meets certain criteria. This ensures that your app does not periodically wake up to do unnecessary work. An app is considered to be a candidate for sleep if: It is not visible—if all of an app's windows are either hidden by other windows or minimized in a hidden dock, and the app is not in the foreground; It is not audible; It has not explicitly disabled automatic termination; It has not taken any power management assertions…" Source: *What's New in OS X v10.9*, <https://developer.apple.com/library/archive/releasenotes/MacOSX/WhatsNewInOSX/Articles/MacOSX10_9.html>. Also the `NSProcessInfo` section of the same page: `beginActivity…` methods are "for temporarily suspending sudden termination, automatic termination, **throttling (App Nap)**, and idle and display sleep."
11. **The three named App Nap measures, and the exit conditions.** **VERIFIED** — "For any app that's not performing important user work, App Nap triggers a number of measures, including: **Priority reduction** … **Timer throttling, which reduces the frequency with which the app's timers are fired** … **I/O throttling**, which reduces the rate at which the app can read or write data from a device while foreground apps need the device." Candour about candidacy: "Generally, an app is a candidate for App Nap if: It isn't the foreground app; It hasn't recently updated content in the visible portion of a window; It isn't audible; It hasn't taken any IOKit power management or NSProcessInfo assertions; It isn't using OpenGL." Exit: "When the user brings the app to the foreground or when the app receives an XPC message or an Apple event, the app is automatically taken out of App Nap and resumes normal execution." Source: *Extend App Nap*, <https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/AppNap.html>.
12. **A status-item-only app is the archetypal candidate (INFERRED, medium-high).** It has no windows to "recently update", is not audible, holds no assertions, and is almost never the foreground app. Field evidence that this is not theoretical: a maintainer commit reading "**LSUIElement processes are prime App Nap candidates when idle, and once App-Napped macOS throttles user-space timers**" (<https://github.com/feschber/lan-mouse/commit/bb1cc805c1c7798c618183016d9eff0b3a32e483>), and an Apple Developer Forums thread where a developer reports App Nap affecting timers and that both `NSAppSleepDisabled` and `beginActivityWithOptions:` "no difference, app still naps" (<https://developer.apple.com/forums/thread/679178>). Apple does not document an App Nap exemption for status items, and HIG explicitly says the system "hides and shows menu bar extras regularly" (see §5), so you cannot infer "visible ⇒ awake".
13. **Therefore: a napping app's periodic poll is not a freshness guarantee, and the design must be honest about that (INFERRED, high).** The correct response is not to fight the OS but to (a) make user-intent refresh authoritative, (b) display the value with its age ("as of HH:MM", monotonic-checked), (c) allow the backstop to be deferred, and (d) never block the UI on a fetch.
14. **If you must stay awake, the sanctioned mechanism is a scoped activity assertion.** **VERIFIED** — `ProcessInfo.beginActivity(options:reason:)` (macOS 10.9+) options include `userInitiatedAllowingIdleSystemSleep` = "A flag to indicate the app is performing a user-requested action, **but that the system can sleep on idle**", and `latencyCritical` = "A flag to indicate the activity requires the highest amount of timer and I/O precision available." Source: <https://developer.apple.com/documentation/foundation/processinfo/activityoptions>. **INFERRED recommendation:** bracket only the user-initiated fetch (hundreds of ms) with `[.userInitiatedAllowingIdleSystemSleep]`, never hold a permanent assertion, never use `idleSystemSleepDisabled`/`latencyCritical` for a background poll, never use the undocumented `NSAppSleepDisabled` Info.plist key.
15. **`NSBackgroundActivityScheduler`: what it promises.** **VERIFIED** — Apple's class abstract is "A task scheduler suitable for **low priority operations that can run in the background**", and the overview: "Use an `NSBackgroundActivityScheduler` object to schedule an **arbitrary maintenance or background task** … it gives the system flexibility to determine the most efficient time to execute based on energy usage, thermal conditions, and CPU use", with intended uses listed as "Automatic saves / Backups / Data maintenance / **Periodic content fetches** / Installation of updates / **Activities occurring in intervals of 10 minutes or more** / Any other deferrable task." `tolerance` "—The amount of time **before or after** the nominal fire date when the activity should be invoked … The default value is half the interval." `repeats` "—If set to true, the activity is **rescheduled at the specified interval after finishing**." `qualityOfService` defaults to `background`. The block "will be called on a serial background queue", the system "automatically uses the `beginActivity(options:reason:)` method … while invoking the block", and failing to call the completion handler "results in the activity not being rescheduled". Source: <https://developer.apple.com/documentation/foundation/nsbackgroundactivityscheduler>.
16. **`shouldDefer` is an energy-state advisory, not a scheduling guarantee.** **VERIFIED** — "If this property contains a value of `true`, system conditions have changed since the time the activity started and deferral is recommended. For example, perhaps the user unplugged the Mac and it's now running on battery power. In this case, your app should finish what it's currently doing, save its state, and invoke its completion handler with a value of `deferred`." Source: <https://developer.apple.com/documentation/foundation/nsbackgroundactivityscheduler/shoulddefer>.
17. **Answer to "is NBAS right for a 20-minute network refresh?": partly.** **VERIFIED + INFERRED.** *Verified:* Apple names "periodic content fetches" and "≥10 minutes" as intended uses, so it is not abuse, and it is the only API that hands the *when* to the system (`dasd`), which is exactly what Apple asks for nonessential network work. *Inferred (medium-high):* it is a poor **freshness** mechanism because the tolerance window is **symmetric** (it may fire before the nominal date), it can be deferred substantially, its `repeats` interval restarts *after* the block finishes, and observed dispatch carries a "Maintenance" classification with a DAS score/priority system — an independent instrumentation write-up of a 10-minute activity shows `DAS SUBMITTING: … at priority 5 with interval 600`, `DAS STARTING <_DASActivity: … "Maintenance", 60s, [window]>`, and `DAS Activity … has preventDeviceSleep 0. PluggedIn state: 1` (<https://eclecticlight.co/2025/02/10/watch-your-background-in-app-background-tasks/>, 2025-02-10). So: use it (optionally) as the deferrable backstop; do **not** use it for the value the user is looking at.
18. **`schedulingAppliesToLowPowerMode` — not found.** **VERIFIED (absence).** The current class reference's attribute list is exactly `identifier`, `repeats`, `interval`, `qualityOfService`, `shouldDefer`, `tolerance` (topic sections "Background Scheduler Attributes"), and targeted searches for the literal symbol returned no Apple documentation. The real Low Power Mode surface on macOS is `ProcessInfo.isLowPowerModeEnabled` (macOS 12+, read-only) with the notification `NSProcessInfoPowerStateDidChange` ("Your app can also register to receive notifications when the Low Power Mode state of a device changes"), and LPM explicitly "**Pausing discretionary and background activities**". Sources: <https://developer.apple.com/documentation/foundation/processinfo/islowpowermodeenabled>, notification doc `NSProcessInfoPowerStateDidChange` (reached via `NSNotification.Name` under Foundation). **UNKNOWN:** whether some non-public/spi property of that name exists; do not depend on it.
19. **Battery is a first-class input.** **VERIFIED** — "Eliminate unnecessary, non-user-driven work and wait for user input. Don't poll for state changes, don't update content on the screen when the user can't see your app, and don't perform power-intensive, discretionary operations when the system is running on battery power." and "Minimize timer usage. If you must use timers, allow flexibility in their timing so they can execute when the system is already awake." Source: *Best Practices*, <https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/BestPractices.html>. (A 2013 Apple technology-overview PDF states the same principle more bluntly — "When the Mac is on battery power, they do only work that the user is requesting or that is absolutely essential" — but I could not fetch that PDF in this run; treat that wording as **search-provider excerpt, not verified**.)

### 3. Event triggers available to a menu bar app

20. **Sleep/wake must be observed on `NSWorkspace`'s notification centre, not the default one.** **VERIFIED** — Technical Q&A QA1340: "These notifications are filed on NSWorkspace's notification center, not the default notification center. **You will not receive sleep/wake notifications if you file with the default notification center.**" <https://developer.apple.com/library/archive/qa/qa1340/_index.html>. (The QA is old but still the canonical statement; the notification docs repeat the requirement for `screensDidWakeNotification`.)
21. **What each `NSWorkspace` notification actually means.** **VERIFIED** (abstracts from Apple's doc JSON): `didWakeNotification` = "A notification that the workspace posts when the device wakes from sleep"; `screensDidWakeNotification` = "A notification that the workspace posts when the device's screens wake" (and its page carries the Important note about using the workspace notification centre); `sessionDidBecomeActiveNotification` = "A notification that the workspace posts **after a user session switches in**"; `sessionDidResignActiveNotification` = "…**before a user session switches out**". Sources: <https://developer.apple.com/documentation/appkit/nsworkspace/didwakenotification>, <…/screensdidwakenotification>, <…/sessiondidbecomeactivenotification>, <…/sessiondidresignactivenotification>. **Interpretation (important gotcha):** the `session*` notifications are about **fast user switching**, not about the app being activated — a menu-bar app that treats `sessionDidBecomeActive` as "the user came back" will miss the ordinary case entirely.
22. **Screen unlock: no documented API.** **UNKNOWN with usable workarounds.** I found no Apple-documented lock/unlock notification on macOS 15/26/27. What the ecosystem uses is the *undocumented distributed* notifications `com.apple.screenIsLocked` / `com.apple.screenIsUnlocked` (plus `com.apple.screensaver.*`), e.g. <https://github.com/hodadako/lumina/blob/6f9bef44/Sources/LuminaApp/SystemStateMonitor.swift> (which the author annotates as noisy, requiring normalization of "WindowServer, power, lock, and screen-saver notifications"), <https://forums.macrumors.com/threads/how-to-know-programmatically-if-a-mac-machine-is-screen-locked.733250/>. Reported fragility: `com.apple.screensaver.willstop` went unreliable in Sonoma 14.1 (<https://github.com/JohnCoates/Aerial/issues/1339>) and the unlock notification does not fire after deep sleep (<https://stackoverflow.com/questions/77939937/>). **INFERRED recommendation:** treat `screensDidWakeNotification` as the practical unlock proxy (the dominant real-world path is display-sleep → lock → display-wake → unlock), and optionally observe `com.apple.screenIsUnlocked` as a best-effort extra with dedupe; never make correctness depend on it.
23. **`NWPathMonitor` is an observer, not a predictor — and it is not edge-only.** **VERIFIED** — type abstract: "An observer that you use to monitor and react to network changes"; `pathUpdateHandler`: "A handler that receives network path updates"; `NWPath.Status.satisfied`: "The path is available to establish connections and send data"; macOS 10.14+. Apple's replacement guidance is explicit and is the reason not to gate requests: on `SCNetworkReachability` (all functions now **deprecated**), "All `SCNetworkReachability` functions are deprecated, because network conditions change too frequently for preflight reachability tests to be accurate and useful. Instead of trying to perform a preflight check, just attempt your connection. The connection may not be available immediately, but you can use `URLSessionConfiguration.waitsForConnectivity` … to automatically connect as soon as it's possible to do so." Sources: <https://developer.apple.com/documentation/network/nwpathmonitor>, <https://developer.apple.com/documentation/systemconfiguration/scnetworkreachability-g7d>. Field evidence that callbacks are not strictly edges: handler called on background→foreground transitions (<https://stackoverflow.com/questions/64108970/>) and no reaction to 100 % packet loss because it tracks route existence (<https://stackoverflow.com/questions/78642753/). **INFERRED:** dedupe by comparing the whole `NWPath` (status + interface + `isExpensive` + `isConstrained`) and rate-limit trigger-driven fetches; treat "satisfied edge" as *recovery*, not as a periodic refresher.
24. **Path properties let you implement Apple's constrained/expensive policy directly.** **VERIFIED** — `URLSessionConfiguration.allowsConstrainedNetworkAccess` (macOS 10.15+) discussion: "Limit your app's of use of constrained network access to **user-initiated tasks**, and put off discretionary tasks until a nonconstrained interface becomes available. To do this, set `allowsConstrainedNetworkAccess` (and `allowsExpensiveNetworkAccess`) to `false` and `waitsForConnectivity` to `true`." When it fails, the error carries `URLError.networkUnavailableReason == .constrained`. Sources: <https://developer.apple.com/documentation/foundation/urlsessionconfiguration/allowsconstrainednetworkaccess>, <…/waitsforconnectivity>.
25. **Clock changes have a dedicated, non-deprecated notification.** **VERIFIED** — `NSSystemClockDidChange` (macOS 10.6+, not deprecated): "A notification posted whenever the system clock is changed. This can be initiated by a call to `settimeofday(_:_:)` or the user changing values in the Date and Time Preference panel. The notification object is null." <https://developer.apple.com/documentation/foundation/nsnotification/name-swift.struct/nssystemclockdidchange>.
26. **App activation is a trap for this app shape (INFERRED, medium).** An `LSUIElement` app with an `NSStatusItem` does not necessarily become the active application when its status item is clicked (which is why apps call `NSApp.activate(...)` explicitly; see <https://osomac.com/2011/04/06/using-nsmenu-in-a-lsuielement/> and common practice in menu-bar apps). **UNKNOWN:** whether `NSApplication.didBecomeActiveNotification` fires on a plain status-item click in macOS 15/26/27. Therefore the trigger must be **your own popover presentation point** (`NSPopoverDelegate.popoverWillShow` / the status-button action), not app activation.

### 4. Energy and etiquette: what the OS asks of you, and a defensible interval

27. **Timer wakeups have a real, named cost, and its structure matters more than the number of polls.** **VERIFIED** — "Whenever a timer fires, the CPU and various other systems wake from their low-power, idle states, incurring an energy cost that adds up over time." (Fundamental Concepts) and, crucially, the fixed-vs-dynamic-cost model: "Tasks your app performs have a *dynamic cost* — how much energy your app uses by doing actual work. They also have a *fixed cost* — how much energy is used by bringing the system and various resources up for your app to do work, and back down after that work is complete. When lots of sporadic work is occurring, there are dynamic costs and a significant fixed cost too… This strategy … results in a tremendous energy savings over time" — with the table "Idle: 10x greater power draw over sleep; 1 % CPU: 10 % greater; 10 % CPU: 2x; 100 % CPU: 10x". Sources: <https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/FundamentalConcepts.html>. **INFERRED:** the dominant cost of a 20-minute poll is the *fixed* cost of waking CPU + Wi-Fi per fire, not the few KB transferred; halving the poll frequency roughly halves that fixed cost, and adding tolerance so the OS can batch your wake with others is worth more than micro-optimising the request.
28. **Network energy: batch, don't scatter; and let the system pick the moment.** **VERIFIED** — "When networking occurs, components such as Wi-Fi and Bluetooth power up and use energy. By batching and reducing transactions, compressing data, and appropriately handling errors, your app can make significant contributions to energy conservation." (Fundamental Concepts); "Nonessential network activity should allow the system to schedule the network activity for optimal times, such as when the Mac is plugged-in or on Wi-Fi." and "Network activity is performed efficiently. It's inefficient to perform network activity over a slow connection. Bandwidth monitoring allows activity to be automatically deferred when throughput falls below a certain threshold. A background session can also defer activity when system thermals rise." plus "Activity self-corrects. URL sessions can be automatically retried when errors occur." Sources: <https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/SchedulingNetworkActivity.html>. **INFERRED:** the Apple-sanctioned "let the system choose" device for this workload is a *background, discretionary* `URLSession`; it is also out-of-process and thus capable of being deferred for a long time, which is exactly why it cannot serve the on-screen number (see §5).
29. **Disk writes cost more than reads — don't persist on every poll.** **VERIFIED** — "Writes to disk require significantly more energy than reads… Writing content to disk should occur only when necessary. Ideally, writes are done in aggregate to achieve higher efficiency." (Fundamental Concepts). **INFERRED:** with "most polls return identical bytes", persist `lastCheckedAt` in memory and only flush prefs/state when the value or the error state *changes* (plus on termination). This also avoids the repo's known `cfprefsd` residue behaviours.
30. **Low Power Mode / thermal.** **VERIFIED** — LPM's documented measures include "Reducing CPU and GPU performance / Reducing screen brightness / **Pausing discretionary and background activities**"; the state is readable and observable (`isLowPowerModeEnabled`, `NSProcessInfoPowerStateDidChange`, macOS 12+). Apple's user-facing naming on current macOS is **Energy Mode** with `Low Power Mode | Automatic | High Power Mode`, settable separately for battery and power adapter, and LPM now also applies to many desktops (macOS Sequoia 15.1+) (<https://support.apple.com/en-us/101613>, Apple Support). Thermal: Apple's background-session doc says discretionary sessions defer on rising thermals, and NBAS "gives the system flexibility … based on energy usage, thermal conditions, and CPU use". **UNKNOWN (unverified in this run):** `ProcessInfo.thermalState` / `ProcessInfoThermalStateDidChangeNotification` availability details on macOS (I did not fetch them); treat as optional input, not load-bearing.
31. **Measured energy of "a tiny periodic HTTPS GET": no authoritative number found.** **UNKNOWN.** I found no Apple measurement. Activity Monitor's own framing is "**Energy Impact: A relative measure** of the current energy consumption of the app (lower is better)" (<https://support.apple.com/guide/activity-monitor/view-energy-consumption-actmntr697/mac>), and external analyses argue it is not a trustworthy absolute metric (Mozilla: <https://blog.mozilla.org/nnethercote/2015/08/26/what-does-the-os-x-activity-monitors-energy-impact-actually-measure/>; Chromium's own `ComputeEnergyImpactForResourceUsage` notes "the below coefficients are not used for now. Their units are unknown, and in the case of the network-related coefficients, it's not clear how to sample that" — <https://chromium.googlesource.com/chromium/src/+/3d997140fc5a0ee822bc50e385c87ebd7393f2da/components/power_metrics/energy_impact_mac.mm>). **INFERRED:** the defensible way to answer "is 30 min OK?" is *relative*: measure `Idle Wake Ups` and the app's CPU/wake time (Apple recommends exactly this: Activity Monitor's Energy pane, the Xcode Energy Impact gauge, and `sudo timerfires -p <pid> -s`) and compare the *fixed cost of one fire* against one unit of interval. Apple's own instrumentation guidance: "If your app has more than one wakeup per second when it should be idle, investigate why" (Timers guide) — a 30-minute poll is ~0.0006 wakeups/s, three orders of magnitude below Apple's stated concern threshold.
32. **Defensible default interval (INFERRED, judgment — no Apple number exists).** Floor: **10 minutes**, because Apple's own API documentation names "Activities occurring in intervals of 10 minutes or more" as the regime for periodic content fetching, and users can always refresh on demand. Default: **30 minutes on power adapter, 60 minutes on battery or Low Power Mode**, with tolerance ≥10 % (Apple's guideline) and a per-install random offset ≤60 s. Keep the existing 1 h "stale" banner only if the freshness path (§5) is implemented — otherwise 1 h of showing an unverified number without a strong affordance is the wrong trade. If the product insists on a 5-minute minimum user setting, label it as a battery-impact choice, and still honour the *floor of 10 min* for the automatic backstop; only user intent may poll faster.

### 5. User intent as the primary mechanism (the load-bearing design decision)

36. **Conclusion for question 5 (high confidence).** Yes: refresh-on-look should be the primary mechanism, with the timer as a backstop. The backstop exists to (a) make the menu-bar title approximately current without the user opening anything, and (b) recover from a failed poll — not to guarantee sub-interval accuracy.

## Deliverable B — Interval / backoff / jitter policy

*All numbers below are **judgment (INFERRED)** except where marked VERIFIED; Apple publishes no recommended poll interval for a user-visible value.*

1. **Freshness window `fresh` = 90 s.** Any trigger class O is a no-op if the reading is younger. Rationale: bounds the worst case for trigger storms (wake + path + look all at once) and makes "look" cheap when the user opens the popover twice.
2. **Backstop cadence.** `nominal = 30 min` on power adapter, `60 min` on battery **or** Low Power Mode; **floor 10 min** even if the user asks for 5 (VERIFIED basis: Apple names "Activities occurring in intervals of 10 minutes or more" as the regime for periodic content fetches); **ceiling 4 h** so the menu-bar title can't age past a working day. User setting remains 5–240 in the UI; the *automatic* backstop clamps to [10, 240] and is widened on battery/LPM.
3. **Tolerance = max(10 % of nominal, 30 s)** — directly from Apple's guideline ("at least 10 percent of the interval", VERIFIED). For a 30 min cadence that is 3 min, which is also exactly `NSBackgroundActivityScheduler`'s default (half the interval would be 15 min — aggressive; 10 % is the macOS *timer* guidance and is a better fit here).
4. **Jitter.** Keep a **persisted per-install random offset** in [0, 60 s] applied to the fire date (decorrelates a user base whose Macs are NTP-synced), plus the OS-visible tolerance above. Do **not** express jitter as extra `tolerance` — tolerance is an *upper bound on delay* handed to the OS for coalescing, not a spread budget. `Timer.tolerance` cannot fire early (VERIFIED), but a dispatch timer **can** (VERIFIED: "the lower limit is under the control of the system"), so if the product ever promises "no more than N requests/hour", enforce it with your own minimum-gap guard rather than relying on the timer.
5. **Backoff.** Keep exponential: `delay = min(1 h, 60 s × 2^consecutiveFailures)`, then apply **full jitter** (`random(0, delay)`) — the current "2× with additive jitter ≤60 s" is equivalent in the long run but full jitter collapses the tail (standard practice; cf. AWS's exponential-backoff-and-jitter write-up, which is a credible engineering source, not an Apple one).
6. **Backoff exemptions.** User intent always fetches (ignores backoff) and resets the counter. 401/403 must not enter ever-growing backoff — surface "key rejected" and stop, since the failure is permanent until the key changes. 429 must honour `Retry-After` if present. `.constrained`/`.expensive` unavailability is a **defer**, not a failure (do not increment the failure counter).
7. **Request hygiene.** Single `URLSession` per intent class, both `ephemeral` (no on-disk cache for an authenticated money value); `httpMaximumConnectionsPerHost = 2`; `timeoutIntervalForRequest ≈ 15 s`; a bounded `timeoutIntervalForResource` (≈60 s) so `waitsForConnectivity = true` cannot turn into a multi-day pending task (**INFERRED**; I did not verify which interval governs the wait, so set both). Opportunistic session: `allowsConstrainedNetworkAccess = false`, `allowsExpensiveNetworkAccess = false`, `waitsForConnectivity = true` (Apple's exact recipe). User-initiated session: both `true`.
8. **Single-flight.** One actor owns fetch state. Concurrent triggers coalesce: an in-flight request is awaited, not duplicated; a `userInitiated` trigger that arrives during an in-flight opportunistic fetch may cancel-and-replace it. Minimum gap between *network attempts* ≈ 60 s for non-user triggers.
9. **Persistence.** In-memory `lastCheckedAt` (monotonic and wall), `lastChangedAt`, `consecutiveFailures`. Flush prefs only on change/terminate.
10. **Display honesty.** Menu-bar title shows the value; popover shows "as of HH:MM" derived from wall clock, and the stale banner when `now - lastSuccess > 1 h` **and** the last attempt failed. After wake, recompute age from wall clock (a monotonic counter may not have advanced during sleep — VERIFIED for `dispatch_time`-based clocks).

## Deliverable D — Failure modes to design for

1. **Sleep through a poll.** The machine can sleep for hours. Because `ContinuousClock` counts sleep and dispatch timers are suspended-then-resumed, the naive loop can produce a burst at wake (overdue sleep + `didWake` + path update). Design: staleness-gated triggers + single-flight + ~5 s debounce window for non-user triggers. Never rely on the timer for post-sleep correctness (Apple does not specify how promptly a woken timer fires).
2. **Overlapping refresh / duplicate requests.** Two triggers in the same second (wake + path + popover). Design: single-flight actor, `fresh` window, minimum gap between network attempts, coalesce pending.
3. **Clock jumps.** NTP correction, user date change, timezone/DST change. Design: monotonic clocks for *intervals* (`ContinuousClock` / `DispatchTime` / `mach_absolute_time`), wall clock only for *display* and for `wallDeadline` arming; react to `NSSystemClockDidChange` by recomputing the next deadline; never compute "time since last fetch" purely from a suspended clock; never compute peak/off-peak labels from local-time arithmetic (already a project rule).
4. **Network flaps.** Dedupe `NWPath` updates; do not preflight-gate; on the satisfied edge, retry only if the last attempt failed; keep opportunistic traffic off constrained/expensive interfaces; bound `waitsForConnectivity` with a resource timeout.
5. **App Nap deferring the backstop.** Accept it. The system exits App Nap on foreground/Apple-event/XPC; your popover-open trigger is the recovery. Do not add permanent assertions to "fix" it.
6. **Popover-open refresh making the UI feel slow.** Render the cached value immediately, show a subtle "checking…" affordance, and never block presentation on the network.
7. **Status item hidden by the system.** Then no poll is visible anyway — another argument for the freshness window and the "as of" label being the contract, rather than a hidden freshness guarantee.
8. **Failure classes conflated.** Distinguish: transport (URLError), HTTP 4xx/5xx, decode failure, keychain/key error. Backoff, retry-after, "stop and ask the user", and "data is stale but valid" are different responses. A decode failure on a 200 must not be silently shown as a fresh value.
9. **Unauthenticated/expensive surprise.** Never send the key to anything but the single allow-listed host; an opportunistic fetch on a mobile-hotspot interface should be suppressed, not merely "cheap".
10. **Timer drift illusion.** Because a dispatch timer may fire *earlier* than the nominal date, do not use it as a rate limiter, and do not log "polled at exactly T".

## Critique of the current implementation (as described)

| Aspect | Verdict | Note |
|---|---|---|
| Fixed 20 min default, user 5–240 | **Acceptable, not optimal** | Inside Apple's ≥10 min regime; but no power-state adaptation and a 5 min floor conflicts with Apple's own framing for periodic fetches. Recommend 30/60 min by power state, floor 10 |
| Backoff 2× per consecutive failure, cap 1 h | **Good** | Add full jitter; exempt user intent; don't grow backoff on 401/403; treat constrained-interface unavailability as deferral, not failure |

| Triggers: launch, wake, NWPath satisfied edge, manual, settings | **Incomplete** | Missing: **popover-open refresh** (the most important one), display wake, will-sleep/displays-sleep pause, Low Power Mode, constrained/expensive awareness, clock-change, session switch, debounce for trigger storms |

## Contradictions and disputed points

1. **Symmetric vs one-sided delay windows.** `NSBackgroundActivityScheduler.tolerance` is "the amount of time **before or after** the nominal fire date", while `Timer.tolerance` guarantees "The timer will not fire before the scheduled fire date". A dispatch timer's lower bound is "under the control of the system". If you assume "tolerance = it may only be late", you will be wrong for two of the three APIs. (Apple docs, all quoted above.)
2. **HIG vs the project's popover.** HIG: "Display a menu — not a popover — when people click your menu bar extra… avoid presenting it in a popover." The project's plan of record uses `NSStatusItem` + `NSPopover` (chosen to dodge the `MenuBarExtra`-only Control Center bug). Both can be true: HIG permits a popover when the functionality is too complex for a menu. Flagged so the exception is deliberate and documented, not accidental.
3. **"A timer fires ⇒ the system wakes" vs a 20–30 min poll being negligible.** Apple's language about wakeup cost ("if a timer causes the system to wake, it incurs that cost"; "more than one wakeup per second when it should be idle ⇒ investigate") does not imply that one wake per 20 minutes is a problem; it implies frequency is the lever. No Apple source gives an acceptable rate for user-visible data — I did not resolve this, and any specific interval is judgment.
4. **`NSAppSleepDisabled`:** still widely recommended on the internet, reported ineffective in a developer-forum test, and absent from Apple's documentation. Recorded, not resolved.
5. **Unverified repository claim (not resolved by this lane):** AGENTS.md asserts a macOS 26 bug where the process exits silently if the user disables the item in Control Center → Menu Bar. I found no Apple documentation of it; conversely, HIG documents that the system *does* hide menu bar extras for space reasons. The macOS 27 notes do document the `NSMenu` image-visibility change (gotcha #7 is corroborated, with `preferredImageVisibility` as the documented fix).

8. **Whether an in-flight `URLSession` task in an App-Napped process is I/O-throttled** ("I/O throttling… reduces the rate at which the app can read or write data"), i.e. whether a poll that starts while napping can be slowed into its timeout.

## Confidence, falsification, and what I could not settle

**Confidence: high** on the shape of the design (on-demand as primary; timer as deferrable backstop; don't fight App Nap; use event triggers for recovery; per-trigger policy classes), because it follows several independent, explicitly worded Apple statements (App Nap candidacy + timer throttling; "primarily in response to user input"; "don't perform power-intensive discretionary operations on battery"; "nonessential network activity should allow the system to schedule"; constrained/expensive = user-initiated only; ≥10 % tolerance; ≥10 min periodic-fetch regime).

**Confidence: medium** on the specific numbers (30/60 min, 90 s freshness window, 1 h cap) — these are judgment, not sourced.

**Confidence: low/UNKNOWN** on: `Task.sleep` tolerance plumbing, post-wake timer promptness, NWPathMonitor behaviour under App Nap, and any absolute energy figure.

**What would falsify my main conclusion:** a demonstration that a windowless `LSUIElement` app with an `NSStatusItem` **never** enters App Nap on macOS 15/26/27 (i.e. the status item counts as "recently updated content in the visible portion of a window"). Test: Activity Monitor → Energy → **App Nap** column for the idle app with its popover closed, plus `sudo timerfires -p <pid> -s` and `Idle Wake Ups` over an hour; if the timer fires on schedule indefinitely and the App Nap column never activates, then a timer-primary design would be reliable and the on-demand emphasis becomes etiquette rather than necessity. Secondary falsifier: if DeepSeek's endpoint gains ETag/`If-None-Match` or a push/streaming mechanism, the cost model (and the interval calculus) changes materially.

**Open questions I could not settle:** items 1–8 in *Missing evidence*; plus which single number Apple's own menu-bar apps use (no public data), and whether Apple would consider `NSBackgroundActivityScheduler` with a 20-minute interval and `repeats = true` "the right tool" for a user-visible datum (their docs support the *category*; nothing addresses the user-visible case).
