# Council memo — can DeepTally be API-only?

**Date:** 2026-09-26 · **Question owner:** @genoma · **Parent:** the orchestrating session

## Question and scope

The user asked DeepTally to *remove the loopback proxy and every harness connection, and read usage only
from DeepSeek's API*. Scope: whether any DeepSeek API surface returns usage, spend, cost, quota or billing
data; whether the web platform's authenticated API is usable; what an API-only app could honestly show; and
what should happen to the proxy. Out of scope: deleting the usage half of the product (an owner decision),
scraping private endpoints (a written v1 non-goal), and any credential probe against the platform.

## Recommendation

**API-only usage history is not obtainable from api.deepseek.com.** DeepSeek hands the `usage` object to the
caller in-band, once per response, and stores nothing queryable: the Responses API is stateless (confirmed
empirically), and every usage-shaped route on the public host is unmounted.

1. **Keep the loopback proxy as the opt-in, harness-agnostic capture point.** It is not a harness
   connection; it is the API boundary itself. Per-harness importers (opencode, pi) are the harness-bound
   path, and the user rejected them.
2. **Add a persisted balance series and show balance *movement* since the last reading** as the honest
   API-only signal, never labelled spend or cost.
3. **Rule out the private platform API** (`platform.deepseek.com/api/v0`): it is the only surface that has
   the data, and using it would require a browser session token lifted from Chrome storage, a third network
   host, and an amendment to both AGENTS.md §1 and PLAN.md §2. It is not a decision for v0.1.
4. **Import DeepSeek's own platform CSV export** — the council's most under-weighted finding. A user
   downloads their usage CSV from the platform in a browser; DeepTally parses the local file. Account-level,
   per-key, per-model, per-day history, no proxy and no harness. Manual and monthly, and the exact columns
   are unverified.

If the user insists on zero non-API components, the honest choice is not to delete the proxy alone: it is to
delete the usage half of the product (ledger and migrations, opencode importer, `LedgerSync`, analytics
panel, CSV import/export, reprice, the unpriced-row machinery, and the usage/import/ledger CLI commands).
That reverses Steps 4–6.5 days before v0.1.0 and must be an explicit decision.

## Accepted and rejected feedback

- **Accepted (researcher, refined):** "hard non-goal" overstates the private-API barrier. The durable
  constraint is AGENTS.md §1 (exactly two hosts); PLAN.md §2 is headed *Non-goals (v1)* and is revisitable
  by plan amendment. Outcome is unchanged: do not use it. A session token is also *worse in kind* than the
  opencode coupling the user rejected: a live account-wide credential this project has no storage policy
  for.
- **Accepted (reviewer, refined):** the balance-movement series belongs in the honest API-only ceiling, but
  must never wear the word *spend*; it should appear only while no local capture is running, difference
  two readings only when both are fresh, keep the sign visible, and state its `$0.01` resolution.
- **Accepted (all):** do not probe the private endpoints with the account key. Two advisors corrected the
  reason: a developer probe is not the app's network policy, but it has **no decision value** (a positive
  result stays excluded) and would send the key to an undocumented third host.
- **Rejected as unjustified:** further endpoint-discovery work. The sitemap, the full changelog, two hosts
  of negative probes, no spec file, three independent implementations and an open feature request all agree.
- **Rejected:** removing the proxy without a replacement. That leaves today-spend, cache-hit, per-model and
  analytics with no source, recreating the `$0.00` confusion with nothing left to fix it.

## Owner decisions (named, not made)

1. Which product ships as v0.1: **balance-and-rates only**, or **balance-and-rates plus local usage
   capture**?
2. If capture stays: opt-in loopback proxy (council recommendation), import-only (harness-bound; already
   rejected by the user), or CSV-only (manual, no live signal)?
3. If zero non-API components is required: confirm the deletion scope (ledger, importer, analytics, CSV,
   reprice, CLI commands) and accept the reversal of Steps 4–6.5.
4. Is the platform CSV import path worth building (verify its columns first)?

## Confidence and what would change the decision

**High** confidence in the API conclusion (sitemap + full changelog + live probes with controls +
documented statelessness + three independent implementations + an open feature request). **Medium** on the
private-API auth detail, deliberately unresolved. The product choice is a values call for the owner.

The decision changes if: DeepSeek publishes a documented, `sk-`-authenticated usage endpoint (history still
starts at adoption); the owner amends AGENTS.md §1 and PLAN.md §2 to permit the platform API; or the
platform CSV columns match an import path DeepTally can support.
